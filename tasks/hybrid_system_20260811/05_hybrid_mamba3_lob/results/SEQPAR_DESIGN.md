# 序列并行：把 4,096 条消息的上下文塞进同样的显存（2026-08-12）

**目标**：上下文 ×8，而**显存、每步 token、步数三项全不变**。

---

## 1. ⭐ 为什么值得做：不是「省显存」，是「白拿 8 倍上下文」

```
现在:  16 GPU 各自持 1 条 2,000 条消息的序列（bsz4 × 500）
       每步 = 16 × 2,000 = 32,000 条消息，上下文 2,000 条

SP4:   每 4 卡合跑 1 条 4,096 条消息的序列，每卡持 1,024 条
       配 bsz=2/组  →  每卡 2 × 1,024 = 2,048 条      ← 与现在几乎相同
       每步 = 4 组 × 2 × 4,096 = 32,768 条            ← 与现在几乎相同
       上下文 = 4,096 条                              ← ×8
```

| | 现行 | SP4 目标 |
|---|---:|---:|
| 每卡每步消息数 | 2,000 | 2,048 |
| 峰值显存（实测外推 `0.42 + 0.03524n`） | 70.9 GB | **72.6 GB** |
| 每步消息总数 | 32,000 | 32,768 |
| **上下文长度** | **2,000** | **4,096** |

`MEM_FRACTION=0.85 ≈ 83 GB`，余量 10 GB。

---

## 2. 为什么在这个模型上特别便宜

**耦合位置的算子恰好三个，全在 mamba3 内部。** Embed、RMSNorm、Dense、half_glu1、
decoder、log_softmax 全部在 L 上逐点独立，沿 L 切开无需任何改动。

> **更正**：本节初稿写的是「只有一个算子」，**错了**。那是照着层的清单推的，不是照着
> mamba3 内部实际算子查的。按语义（凡是把不同位置牵到一起的）重新搜，得到三个：

| # | 位置 | 算子 | 载荷 | 难度 |
|---|---|---|---|---|
| 1 | `mamba3_jax.py:183` | SSD Phase 5 全对状态传播 | 655 KB/层/序列 | **已完成** |
| 2 | `mamba3_jax.py:140` | `cumsum(angles_scaled, axis=0)`，RoPE 角度沿 L 累积 | (nh, 32) ≈ 2.5 KB | 小 |
| 3 | `mamba3_jax.py:267` | `Trap_shifted = pad(Trap_sig[:,1:], (0,1))`，沿 L 平移一位 | (nh,) ≈ 80 B | 小 |

第 2 项与 Phase 5 是同一个模式：本地前缀和 + 设备总量的独占前缀。
第 3 项只需要邻居的**第一个**元素，一次单元素 halo 交换（`ppermute`）即可。
两者载荷都比 Phase 5 小三个数量级，**不改变 §2.3 的通信结论**。

顺带确认了 `lob_seq_model.py` 里那四处 `cumsum` 都在 `running_mean` /
`numpy_ewma_v2` / `ewma_vectorized*` 里，**不在训练前向路径**
（`__call_ar__ → __call_training__`），无需处理。

**这条更正本身是方法**：断言「只有一个非本地算子」时我读的是层的清单；
真正该做的是**按语义搜「凡是把不同位置牵到一起的」**——`cumsum`、`scan`、`roll`、
切片错位、`pad` 后对齐。这与本任务先前那次「按语法搜漏掉 `runtime/inference.py`」
是同一个教训的第二次出现。

### 2.1 Phase 5 的实现与它的注释不符，而这对我们有利

`mamba3_jax.py:183` 注释写「cross-chunk **sequential scan**」，实现却是全对形式：

```python
decay_chunk = jnp.exp(segsum(A_end_padded))      # (nh, nc+1, nc+1)
new_states  = einsum('hzc,chpn->zhpn', decay_chunk, states)
```

这是 **O(nc²)**。4,096 条消息时 nc = 1,664：

```
Phase5 FLOPs = 2 × nc² × nh × hd × N
             = 2 × 1664² × 20 × 64 × 128
             = 2 × 2.77e6 × 163,840
             = 9.07e11            ≈ 907 GFLOPs / 层 / 样本
```

切成 D 份后每设备只做 `(nc/D)²`，**四设备合计 nc²/4——总计算量降 4 倍**。
SP 在这一项上不是付通信换显存，是**同时省显存和省计算**。

### 2.2 分解：设备边界与块边界是同一件事

块递归是仿射的（`state_out = exp(A) · state_in + local`），所以可结合，
**跨设备那一步就是同一个全对公式向上提一层**——4 个元素而不是 1,664 个。

本地那一半**不需要任何新代数**：参考实现算出 `new_states` 有 `nc+1` 项然后
`states = new_states[:-1]` 把最后一项丢掉，而**那个被丢掉的项正好就是「离开本设备的状态」**。

```
每设备做:  local_all_pairs (nc/D+1)²   →  states_in[本地] 与 state_out[出口]
跨设备:    all_gather(T_d, S_d) → (D+1)² 全对 → carry_d
合成:      states_in += exp(本设备起点到各块的衰减) × carry_d
```

### 2.3 通信量可以忽略

```
每层每序列 all_gather 的载荷 = nh × hd × N × 4 bytes
                            = 20 × 64 × 128 × 4
                            = 655 KB

每设备每层收 3 × 655 KB ≈ 2 MB
每步 = 10 层 × 2 序列 × 2 MB = 40 MB
NVLink 每 GPU 聚合 478 GB/s  →  约 0.08 ms 前向，含反向约 0.25 ms
```

对约 1.2 s 的步时**可以忽略**。

## 3. ⚠️ 整除约束：目标是 4,096 条不是 4,000 条

```
nc = n_msgs × 26 / 64
要求 nc 能被 D=4 整除
  → n_msgs × 26 被 256 整除
  → n_msgs × 13 被 128 整除
  → n_msgs 必须是 128 的倍数

4,000 / 128 = 31.25   ✗   nc = 1,625 = 5³ × 13，除以 4 得 406.25
4,096 / 128 = 32      ✓   nc = 1,664，每设备 416 块
```

**先把这个算清楚**，否则会在跑起来之后才以 padding 或静默丢弃的形式暴露——
而静默丢弃正是本任务已经栽过一次的那类问题。

## 4. 已完成：扫描本身，且数值一致性可证

`src/s5/mamba3_seqpar.py` + `src/s5/tests/test_mamba3_seqpar_parity.py`（commit `a69bf05`）

分片是**重结合求和，不是近似**：本地全对覆盖设备内的有序对，设备级全对覆盖跨设备的，
两者合起来对每个 `(c ≤ z)` 恰好覆盖一次。所以与非分片版的唯一容许差异是浮点重结合。

测试跑在 4 个 host 设备上，**不占 GPU**，查两件会以不同方式失败的事：

| 检查 | 抓什么 |
|---|---|
| 与非分片参考一致 | carry 的代数错误 |
| D=2 与 D=4 结果相同 | 只在某个特定 D 下碰巧对的 carry |

**并且验证了测试会红**（一个在修好和修坏时都通过的测试等于没有测试）：

| 注入的 bug | D=2 相对误差 | D=4 相对误差 |
|---|---:|---:|
| 丢掉跨设备 carry | 55.2% | 70.8% |
| carry 取错设备下标 | 55.2% | 70.8% |
| 还原 | 4 passed | 4 passed |

（两者表现相同是对的：`H_all[0]` 恒为零，首设备本就没有前驱，所以取错下标等价于丢掉 carry。）

## 6. 与 remat 的关系

`remat` 也能让 4k 装下，而且只要几行（给 `init_Mamba3SSM` 加参数并包 `nn.remat`），
但两者不等价：

| | remat | 序列并行 |
|---|---|---|
| 显存 | ~3–5× | D 倍 |
| 计算 | **+30%**（重算） | **−D 倍**（Phase5 的 nc²） |
| 可扩展性 | 到此为止 | 继续加卡可继续加长 |
| 改动量 | 几行 | 六项，其一是本文件 |

**结论**：remat 是让 4k 立刻能跑的最短路径，SP 是让上下文继续长下去的路径。
两者不冲突，可叠加。
