## 5. 根因之一：`SLURM_TIMELIMIT` 被写死成 5 小时

启动脚本里（从 `launch_attach_hybrid.sh` 原样继承）：

```bash
export SLURM_TIMELIMIT="05:00:00"
export SBATCH_TIMELIMIT="05:00:00"
```

**srun 会把 `SLURM_TIMELIMIT` 当作这个 step 的时限来读。** 于是无论
`MAX_JOB_HOURS` 设成多少、无论分配还剩多久，训练都在整 5 小时被杀：

```
5992008.1116  TIMEOUT  0:15  Elapsed 05:00:21  nid[011166-011167]   hybrid
5992008.1151  TIMEOUT  0:15  Elapsed 05:00:21  nid[011101,011165]   baseline
```

两条臂**同样的 Elapsed，同样的 State**——同一个原因。

**为什么 `MAX_JOB_HOURS=13.5` 没用**：它管的是训练脚本自己的优雅停机，在更内一层；
srun 的 step 时限在更外一层，先到先杀。设一个内层的宽限，挡不住外层的硬限。

**已修**：时限改为从 `squeue -j <alloc> -h -o "%L"` 推导，留 10 分钟收尾。
续训时实测打印 `[time] step 时限设为 09:24:00（分配剩 9:34:29）`。

## 6. 排除：不是 bf16

`registry.py` 只在 transformer/nsa 分支算 `dtype`（421 行）；**hybrid 分支调
`init_TransformerBlock` 时根本没传 dtype**，用默认 `jnp.float32`。
所以 attention 是 fp32 跑的，「52,000 项 softmax 在 bf16 下失精」这个候选出局。

## 7. 正在做的定位

从 checkpoint **2000**（loss 0.789，离 baseline 0.720 还近）重启，**不做任何修改**，
只把 `CHECKPOINT_EVERY` 从 2000 降到 **250**，跑到 6000。

`step_loss` 是在 checkpoint 回调里记的（`train.py:578`），所以记录频率就等于
checkpoint 频率——这也是为什么先前只能把发散定位到「4000–6000 之间」这么粗。

三种读数各自对应不同结论：

| 曲线形状 | 意味着 |
|---|---|
| 某一步突然跳到 3+ | 单批数据或数值事件，查那一批 |
| 从 4000 起持续爬升 | 优化不稳，动 LR/warmup（但要两臂同改，否则破坏对照） |
| 这次不发散 | 上次是瞬态，需要更多 seed 才能判 |
