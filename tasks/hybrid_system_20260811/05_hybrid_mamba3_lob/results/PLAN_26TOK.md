## 0. 先把「26 tok plan」这个题目的实际含义钉住

现行编码**已经是 26 tok**（`src/lob/encoding.py:351`，`TOK_LENS` 求和 = 26）。所以 (8) 不是「迁移到 26tok」，而是**26tok 已知失败模式的处置方案**。

失败模式只有一个，但它有两个名字：

| 从训练侧看 | 从生成侧看 |
|---|---|
| 26 位里 10 位是 ref 字段（price_ref / size_ref / time_s_ref / time_ns_ref），近乎确定性，稀释 per-token loss | **一次必须精确命中的三重匹配，而 time 命中不了** |

**后者才是主叙述**（既有教训 L306）：前者只是效率问题，后者是正确性问题，直接决定引用解析成不成功。

## 1. 瓶颈的量化：三份独立证据指向同一处

| 证据 | 数值 | 出处 |
|---|---|---|
| 键本身完美 | 可见目标中纳秒精确时间**唯一性 = 100%**（27,789/27,789） | cascade 审计 |
| 但模型说不准这个键 | L1 精确命中 74.89%（全池 3,136） | 本任务 `refer_success.py` |
| 且随距离恶化 | 96.45%（≤10 条）→ 74.57%（101–250 条）→ 39.16%（窗口外） | 本任务阶段2 |
| **模型对纳秒大数本身就弱** | R7 线实测：**完整字段准确率仅 0.62%** ⇒ `ref_age_ns` 方案已否决 | BPE R7 线（Codex 侧） |

最后一行是决定性的补充：**问题不只是「记不住」，而是「纳秒级大整数这种目标形态，模型本来就预测不准」**。这解释了为什么 L1 天花板压得这么低，也直接决定了候选设计的取舍。

## 2. 三个候选设计（沿用既有审计的命名）

| 设计 | 内容 | 保住什么 | 代价 |
|---|---|---|---|
| **A** 27tok 兼容 L3 | 保持 L1/L2 不动，只在 1,201 条残差上调用指针 | 保住已发表的 96.14% any-live-ID | 纠正不了 L2 那 6,475 次**可能选错对象**的解析 |
| **B** 27tok pointer-first | 预测 **reverse NEW rank**，解析到真实历史行与 order id，再回退时间戳、再回退同价毫秒 | 同时改善**语义正确性**与 live-ID 成功率 | 窗口 13,000 → 13,500 tok（+3.85%）；需重训 |
| **C** 26tok 复用字段 | 复用一个 resolver 用不到的既有 ref 字段承载指针 | 保住 13,000 token 窗口 | 抹掉该字段旧义；仍需重训与干净消融 |

指针标签三选一的熵对比（既有审计实测）：

| 标签 | 观测范围 | 熵 | top-1 频率 |
|---|---|---|---|
| 绝对消息索引 | 0..498 | 8.5421 bit | 0.433% |
| 后向消息距离 | 1..486 | 6.9938 bit | 8.126% |
| **reverse NEW rank** | 1..241 | **6.0525 bit** | **10.374%** |

词表 0..999 已存在，**无需扩表**。

## 3. ⭐ hybrid 的结果如何改变这个取舍

阶段3 给出的新事实：**不动编码，只把主干一层换成全局 attention**，在 step 12000 上：

| 引用年龄 | baseline | hybrid | Δ |
|---|---:|---:|---:|
| 26–50 | 80.20% | 85.63% | +5.44 |
| 51–100 | 69.21% | 78.60% | +9.40 |
| **101–250** | 48.83% | **61.63%** | **+12.79** |
| 窗口之前 | 26.80% | 29.36% | +2.56 |

由此得到三条对 (8) 的直接影响：

### 3.1 两条路线攻击的是同一个失败，且**可叠加**

27th pointer 的本质是 **pointer network**，而 pointer network 就是 attention。区别在于：

```
        隐式修法（hybrid）                    显式修法（27tok 指针）
   ┌────────────────────────┐          ┌────────────────────────┐
   │ attention 层在内部按内容 │          │ 直接输出一个指向历史行 │
   │ 回查历史，从而把纳秒键   │          │ 的小范围整数索引，      │
   │ **说得更准**            │          │ **绕过纳秒键**          │
   └────────────────────────┘          └────────────────────────┘
        受限于「能不能说准」                受限于「指得对不对」
        天花板 = 可见性 88.18%              天花板 = 可见性 88.18%
```

两者天花板相同（都受可见性限制），但**失败方式不同**：hybrid 仍要模型吐出一个纳秒大数（R7 实测这类目标准确率极低），指针则把目标换成一个 6.05 bit 的小整数。**所以叠加是有意义的：attention 提供回查能力，指针提供一个模型更容易命中的输出形态。**

### 3.2 优先级应当调整

既有审计推荐 **B（pointer-first）**。加入 hybrid 的证据后我仍推荐 B，但**理由变了**：

- 原理由：B 能同时改善语义正确性与 live-ID 成功率。
- 新理由：**R7 已证实模型对纳秒大数的完整字段准确率只有 0.62%**。这意味着 hybrid 把 L1 从 48.83% 抬到 61.63%（101–250 档）已经是在一个**目标形态极不友好**的任务上取得的；换成 6.05 bit 的指针后，同样的 attention 能力应当兑现得更充分。**B 的收益在有 attention 的主干上应当比在纯递归主干上更大。**

### 3.3 正交性与实验序

hybrid（架构）与 27tok（编码）是**两个正交变量**，同时改会让归因不可能。执行序：

| 阶段 | 内容 | 判据 |
|---|---|---|
| **S0** | hybrid@32000 vs baseline@32001 四项对照（进行中） | 固定架构效应 |
| **S1** | 在**已定架构**上实施设计 B，重训 | 与 S0 同架构、同数据、同步长 |
| **S2** | 2×2 消融：{mamba3, hybrid} × {26tok, 27tok} | 分离两条路线的贡献与交互 |

S2 的四格是最终交付形态。若算力只够三格，**砍 {mamba3, 27tok}**——因为它是三者里最不可能被采用的组合。

## 4. 实施 B 的技术清单

| # | 事项 | 依据 |
|---|---|---|
| 1 | 第 27 位承载 `ref_new_rank`（reverse NEW rank，范围 1..241 观测） | 熵最低、top-1 最高 |
| 2 | 复用词表 0..999，**不扩表** | 既有审计 |
| 3 | 解析序改为 `pointer_exact_live_id` → `exact_timestamp` → `same_price_closest_millisecond` | cascade 审计推荐 |
| 4 | 指针解析后**必须校验**：该 id 仍在活簿、方向一致；用被引用单修正 event price；夹住数量 | 防「指到一个合法但错误的对象」 |
| 5 | 窗口从 500 消息 × 26 = 13,000 变成 × 27 = 13,500（+3.85%）；若要守住 13,000 上限则只能放 481 条消息 | 既有审计算过 |
| 6 | 试点期**即使前级已成功也要算出指针并记录一致率**，但不允许它覆盖旧 resolver | cascade 审计的明确要求 |
| 7 | 报告口径必须含：exact-target 正确率、any-live-id 成功率、L1/L2/L3 增量、非法/窗口外索引率、resolver 冲突与选错率 | 同上 |

### 一条必须写进代码注释的红线

> **不要把 masked-pointer 的 100% validity 叫作 100% reference prediction。**

既有审计实测：1,201 条残差里每一条都至少有 5 个活的同侧历史 NEW 候选（中位 21、p90 42、max 294）。一个只允许合法索引的掩码**必然**能产出某个活 id，把 any-live-ID 机械抬到 100%——但那是「撤了某一单」，不是「撤对了单」。这与既有教训「回退到粗精度 ≠ 容忍误差」同形。

## 5. 预期收益的上下界（供决策，不是承诺）

| 情形 | any-live-ID 合计 | 依据 |
|---|---|---|
| 现状（26tok，纯 mamba3） | 96.1435% | 既有审计 |
| 指针在 1,201 条残差上恢复 25% | 97.11% | 线性外推 |
| 恢复 50% | 98.07% | 同上 |
| 恢复 88.18%（可见性 oracle） | **99.54%** | **乐观上界，非训练模型准确率** |

**但这张表用的是 any-live-ID 口径，会高估。** 主判据应当是 exact-target。R7 线的 teacher-forced exact-target 三方对照（26tok 86.28% / R6 96.78% / R7 98.24%）说明：换到正确口径后，各方案的排序与差距都会变，**立项前提若建立在 any-live-ID 上就是错的**。设计 B 的收益必须用 exact-target 重新估。

## 6. 现在不做什么

| 不做 | 理由 |
|---|---|
| 现在就改编码 | 架构变量还没固定（S0 未完成），同时改两个变量等于放弃归因 |
| 用 `ref_age_ns` 作指针 | R7 已否决：模型对纳秒大数完整字段准确率仅 0.62% |
| 用 any-live-ID 作主判据 | 它被 L2 的无阈值兜底抬高，且既有分析已证明它会误导立项 |
| 扩词表 | 0..999 已够用 |
