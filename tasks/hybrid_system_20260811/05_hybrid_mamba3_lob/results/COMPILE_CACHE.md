# XLA 持久化编译缓存：能省多少、怎么失效（2026-08-13）

## 1. 先把数字纠正过来

会话里一度说「每次启动 compile 要花 8 分钟」。实测不是：

```
12:58:29  launcher 起
13:01:16  进入训练循环        ← 2m47s：preflight + 挂 48 个 squashfs 分片
                                 + JAX 分布式 init + 载 checkpoint
          第一步 [00:50<      ← XLA 编译训练步 = 50 秒
          之后 ~1.3 s/步
```

**重启到稳态约 3.5 分钟，其中编译占 50 秒。**

那个「8 分钟」是 2026-08-13 10:11–10:19 **baseline 被邻居挤死**那一次的耗时，
里面含 JAX 分布式 init 的 2 分钟超时 —— **那是故障时长，不是启动时长**。

所以编译缓存能省的是每次重启 **~50 秒**。今天重启了 3 次，合计约 2.5 分钟。
剩下的大头（挂载、init）缓存救不了。

## 2. 接法

两个 launcher 各加一段，按配置分子目录：

```bash
JAX_CACHE_ROOT=${JAX_CACHE_ROOT:-$WORKDIR/.jax_cache}
_CACHE_SIG="${ARCH_TAG}_n${NNODES_ATTACH}_L${MSG_SEQ_LEN}_b${PER_GPU_BSZ}"
export JAX_COMPILATION_CACHE_DIR="$JAX_CACHE_ROOT/$_CACHE_SIG"
export JAX_PERSISTENT_CACHE_MIN_COMPILE_TIME_SECS=1.0   # 低于 1 秒的不值得存
export JAX_PERSISTENT_CACHE_MIN_ENTRY_SIZE_BYTES=0
```

分子目录有两个理由：不同配置（架构/节点数/序列长度）的产物本来就互不复用；
单个目录在 Lustre 上无限膨胀是元数据负担，分开放也便于整目录丢弃。

## 3. 失效机制：不用自己设计

JAX 的缓存键（`jax/_src/cache_key.py:get`）哈希了：

| 组成 | 换了会怎样 |
|---|---|
| **computation（HLO 模块）** | 代码改动只要改变了生成的 HLO，键就变 |
| jaxlib 版本 | 换 JAX 自动失效 |
| backend / platform | 换硬件自动失效 |
| XLA flags | 改 XLA 开关自动失效 |

> **它键在编译产物上，不是键在源码文本上。**

两个方向都对：改注释、改 print、改日志不会失效（HLO 没变，本就该复用）；
改一行影响计算图的代码则必然失效。不存在「改了代码但缓存没失效」这种危险，
也不存在「只改注释却全量重编译」这种浪费。

## 4. 实测验证（三段）

同一个缓存目录，跑三次；variant B 只比 A 多一行 `x = x * 1.0000001`：

| 场景 | cache miss | cache hit | 新增条目 |
|---|---:|---:|---:|
| 冷启动 | 4 | 0 | +1 |
| **同代码再跑** | **0** | **4** | **0** |
| **改了一行代码** | **1** | **3** | **+1** |

第三行是这套机制的关键证据：**改一行代码 → 恰好 1 个 miss + 3 个 hit**。
只有被改动影响到的那个可执行体重编译，其余继续复用。

> 失效不是「全有或全无」，而是**逐个可执行体的粒度**。
> 按源码文件哈希的方案做不到这一点 —— 动一行就得全量重编译。

## 5. 注意

- 多主机下 16 个进程会编译同一个模块并写同一个键。JAX 用临时文件 + rename
  保证原子性，代价是一次性的冗余写，可接受。
- 缓存**不会自动淘汰**。按配置分目录已经把增长限制住了；若某个配置废弃，
  直接把它那个子目录整个删掉。
- 首次跑新配置时缓存为空，仍要付那 50 秒 —— 这是一次性的。
