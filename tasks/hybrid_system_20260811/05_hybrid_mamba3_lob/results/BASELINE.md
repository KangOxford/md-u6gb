## 3. ⭐ 预注册的主判据（先定义再测，防止事后挑指标）

### 3.1 为什么主判据是 (7.4) 而不是 (7.3)

`findings.md:1379` (F234) 的对照实验：把生成窗口内的**时间顺序完全打乱**后，LOB-Bench WS-21 反而**好 13.7%**（0.1441 → 0.1244），21 个特征里 **13 个恰好 ±0.0%**。

```
   打乱生成窗口的时间顺序 → WS-21 从 0.1441 变成 0.1244（更好 13.7%）

   ┌──────────────────────────────────────────────────┐
   │ 21 个特征对「时间顺序」的敏感性                   │
   ├──────────────────────────────────────────────────┤
   │ 13 个 恰好 ±0.0%   ← 纯逐行边际量（深度/量/spread）│
   │  4 个 真正变差     ← ofi 族（唯一含顺序信息的）    │
   │  4 个 反而变好                                    │
   └──────────────────────────────────────────────────┘
```

**结论**：LOB-Bench 测的是**边际分布**，不是**动态**。命题 H 主张的「精确回指历史某条订单」是纯动态能力，(7.3) 结构上就测不到。**若把 (7.3) 当主判据，等于用一把测不到目标量的尺子做裁决。**

### 3.2 主判据：引用解析的 L1 精确命中率，及其 oracle 上界

```
  75.35%  ├─────────── 12.83 pp 可夺取空间 ───────────┤  88.18%       100%
 baseline                                        可见性 oracle    理论上限
 L1 精确                                                          (够不着)
 (23,466/31,142)          hybrid 该填掉多少？          剩 11.82% 的目标
                          ← 预注册判据 →              早于条件窗口
```

依据（`research/B_baseline_results_raw.md` §4.1）：在 paired-255 的真实续段里，目标 NEW 可见率 88.18%（cancel/delete），而**在可见目标中，纳秒精度的精确引用时间唯一确定目标 = 27,789/27,789 = 100%**。

> 这一条把「表示问题」和「能力问题」切开了：键本身完美（100% 唯一），所以 75.35% → 88.18% 的缺口**全部**是「模型记不住那个纳秒键」的内容寻址能力缺口，而不是编码缺陷。这正是 attention 的本职。

**预注册判据**：

| 判据 | 阈值 | 性质 |
|---|---|---|
| **P1 主判据** | L1 精确命中率相对 baseline 提升，且**配对块自举 CI 不跨 0** | 判定命题 H 成立/不成立 |
| **P2 机制判据** | 成功率对「被引用订单年龄」的**斜率差** Δ_slope：baseline 随年龄下滑而 hybrid 更平 | 比单点差强得多的机制证据 |
| **P3 非劣效闸门** | LOB-Bench WS-21 不劣于 baseline 超过噪声底（见 §4） | 防止「赢了回指、毁了分布」 |
| **P4 守门员** | perplexity 不显著恶化 | **已知失灵**（见 §5），仅作粗筛 |

### 3.3 为什么 P2 比 P1 强

被引用订单的「年龄」（往回多少条消息）分布本身是长尾的（规则 A6）。若 hybrid 的优势真的来自内容寻址，它应当**随年龄增长而放大**——递归状态压缩越久的历史越失真，attention 则几乎无损。反之，若两臂的增益在各年龄段上均匀分布，那更像是训练噪声或容量差，而非机制。

```
 成功率
   │
   │ ●━━━●━━━●━━●━━●          hybrid（预测：更平）
   │ ○━━━○━━○━━╲
   │              ○━━╲         baseline（预测：随年龄下滑）
   │                   ○
   └────────────────────────▶ 被引用订单年龄（往回消息数）
     近                                         远（长尾）
```

| 来源 | 散布 | 出处 |

## 5. 两条会让人得出错误结论的陷阱

### 5.1 perplexity 作为守门员几乎失灵

`findings.md:2853` (F296)：同一改动使 **CE 只 +0.815% 而 LOB-Bench KS +102%**。

> 推论：(7.1) 只能当粗筛（「模型是不是彻底坏了」），**不能**当「模型没变差」的证据。任何 perplexity 闸门必须配分布级闸门。

### 5.2 跨编码/跨池的数字不可并排

| 陷阱 | 具体 |
|---|---|
| 两个评测池 | M1/M2/M4 用 `0c41de51…`（226,002 序列），M3/M6/M7 用 `4909799c…`（最大索引 21,728），**交集 1.5%**。旧的 0.0438 绝不能进本表 |
| 子集 ≠ 全池 | 取的是冻结池**开头** N 个而非随机 N 个；M1 的子集/全池系数 = **1.1445**。混用 0.20714 与 0.23708 会凭空造出 14% 假差距 |
| fix 前后两套评测 | model_zoo mamba3 必须用 `evaluation_30k_mamba3_fix_b1868a4`，旧版差 1.5 倍 |
| per-token loss 跨编码 | 26tok 每条消息 26 位里 10 位是近乎确定的 ref 字段，白送分母；跨编码要比就比**每条消息的 nats** |
| 坏 harness | `tasks/bpe_varlen_torch_20260806T183132Z` 的 0.2748 是自建 harness 打残的结果（同模型正确 harness 为 0.20714），且那是 PyTorch Transformer **不是 Mamba3** |

## 附注（2026-08-12）：日志里的「16 BSZ」是每进程，不是全局

查 2k 上下文可行性时读到 `[Resume] Sampler skip: ... (12000 batches × 16 BSZ)`，
一度据此认为全局批量是 16、每卡 1。**那是误读**，此处记下来免得再犯：

```
srun --ntasks-per-node=1     →  每节点 1 个进程，进程内管 4 张卡
每进程批量 = PER_GPU_BSZ × GPUS_PER_NODE = 4 × 4 = 16   ← 日志里的 16
全局批量   = 16 × 4 节点 = 64                            ← 上表的 64，是对的
```

佐证：tqdm 总数 939,147 = 15,026,365 / 16，即那个 15,026,365 是**本进程**的分片。

**判据**：DistributedSampler 的计数是**每 rank** 的。看到一个批量数字先问它属于哪一层
（每卡 / 每进程 / 全局），三个数彼此差 GPUS_PER_NODE 和 NNODES 两个因子。

**这个数为什么要紧**：`PER_GPU_BSZ=4 × 500 条` 与 `PER_GPU_BSZ=1 × 2000 条` 都是每卡每步
2,000 条消息。实测两者显存也相同（约 71 GB 对 70.9 GB）——**递归模型的显存只取决于消息
总数，与怎么切成样本无关**。所以换到 2k 上下文可以做到显存、每步 token、步数三项全不变，
是一个没有算力混淆的受控实验。
