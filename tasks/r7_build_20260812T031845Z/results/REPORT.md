# R7 报告：用一个零成本的约束替换三个新字段

时间：2026-08-12T04:15Z
状态：**build / 对抗审查 / 推理 / bench 全部完成**。训练：R7 不需要重训（见 §2）。

---

## 摘要

R7 的原计划是给 touch 消息新增三个字段（`ref_size` / `ref_age_ns` / `ref_index`）、
改成三通道投票解析、重训一个模型，去攻 R6.1 相对 26tok 落后的 18.07 pp reference 缺口。

**两轮对抗审查 + 五组只读实验把这个计划否掉了，换成一个零 token 成本、纯推理侧、
不需要重训的改动：把消息自带的 `quantity` 从"输出字段"升级为"解析硬约束"。**

关键数字：

| 项 | 值 |
|---|---|
| `(side, price)` 唯一识别率 | 63.8562% |
| **加 `quantity` 硬约束** | **85.8253%**（零新增 token，误选 0） |
| 加新字段 `ref_size` | 86.3003%（+0.4750 pp，需 +1 字段） |
| `ref_n` 偏 ±1 时 R6 的 exact-target | **0.0000%** |
| `ref_n` 偏 ±1 时 R7 的 exact-target | **92.44% – 93.29%** |
| 生成时解析失败率 `ref_no_book`（255 序列全量） | 12.75% → **11.56%**（降 9.3%） |
| LOB-Bench 三项 vs 26tok | **全胜**：WS −30.4% / KS −9.2% / L1 −14.2% |
| LOB-Bench 三项 vs R6.1 | +2.49% / +0.84% / −0.70%，**落在复跑噪声（1.9%）量级** |
| 训练成本 | **0**（纯推理侧改动，用 R6.1 的 step-9000 checkpoint 直接跑） |

## 1. 原计划为什么被否

### 1.1 靶子的余量比想象的小

把 R6.1 落后的 18.07 pp 拆开（`generation_quality_audit.json` + 16 个 shard 日志）：

| 成分 | pp | 三个新字段能修吗 |
|---|---:|---|
| 结构天花板（目标早于 condition 窗口） | 12.1435 | 不能 |
| `ref_raw` 分支（窗口外引用，模拟簿无真实 id） | 9.86 | 不能，**同一个结构问题** |
| 真正的 key 预测错误 | **≈ 0.28** | 能——只有这么多 |

`ref_raw` 是 R6 解析的第二条路径：目标早于编码流时，直接把负数码解回**真实历史
order_id**，**不查簿**。但生成侧的模拟簿是从 L2 快照初始化的，bookinit 用的是
900,000,xxx 合成 id，真实 order_id 在其中不存在 → 重放必然判非 live。而 provenance
写的是 `3 if ref_status == "fallback" else 1`，所以 `ref_raw` 被**记为成功**。

对账：若 `ref_raw` 全部非 live，live 应等于 `ref_book` = 24,774；审计实测 24,309，
差 465（1.9%，来自日志口径含 EXECUTION 而审计 `cancel_rows` 不含）。假设成立。

**结论：那 9.51 pp 不是可修的 bug，是结构天花板被 provenance 错记成了成功。**

### 1.2 三通道投票是伪冗余

原设计的三通道 T（`ref_age`）/ C（`ref_size`）/ I（`ref_index`）中，**T 与 C 同源**：
都从 reference 字段读值、都在 `(side, price)` 池内定位。模型若整体 copy 错一笔订单，
二者会一致地指向它，凑成两票"共识"。

误差注入实测（τ=1μs，多数决）：

| 注错场景 | 命中% | **撤错单%** |
|---|---:|---:|
| 单通道出错（T/C/I 任一） | 86.3 – 100 | **0.0000** |
| **T+C 同时混淆** | 63.8562 | **21.2710** |

而这 21.27% **全部来自 `consensus`**（`single_wrong` = 0）——错误伪装成高置信共识。
四种裁决规则都救不了：改成"共识须含 I"或"T+C 折叠"确实把撤错单压到 0，
但把系统命运绑死在 I 上（I 一错位，命中从 86.5055% 崩到 **0.2051%**）。
**问题不在规则，在于只有两个独立信息源。**

### 1.3 `ref_age_ns` 无条件编码会自我拆台

实测 27,789 个引用里有 **27,676 个互不相同的 `ref_age` 值**，词表的 HEAD 频率表
基本失效（top-4096 个专属 ID 只覆盖 15.15%）。走 SHORT/LEN 路径平均 **3.5 token/条**，
touch 约占消息流一半，整体消息均值会从约 6 涨到约 7.7（+29%）。

固定 13,000 token 上下文下可装消息数掉 **22.5%** → 条件窗口变浅 → 目标可见率下降
→ **R7 自己的天花板被这个为提高精度而加的字段压低了。**

## 2. 换成什么

### 2.1 `quantity` 是一个被浪费的独立信息源

`quantity`（本次修改量）是**消息自身字段**，26tok 与 R6 都已在预测它，
但两者的 resolver 都只把它当输出、没当作对候选订单的约束。

约束语义与实测过滤力：

| 事件 | n | 目标满足 `q==remaining` | 干扰订单通过 |
|---|---:|---:|---:|
| delete | 27,205 (97.9%) | **100.00%** | **20.57%** |
| execution | 520 | 78.08%（用 `>=` 则 100%） | 63.14% |
| partial_cancel | 64 | 0%（用 `>=` 则 100%） | 8.89% |

对占 97.9% 的 DELETE，约束**永不误杀正确答案**，却过滤掉 **79.43%** 的干扰。

### 2.2 裁决顺序（刻意保守）

```
|可行集| == 1                 -> 用可行集那一笔（最可靠，不看 ref_n）
ref_n 的结果 ∈ 可行集         -> 用 ref_n 的结果（约束与排名互相印证）
ref_n 的结果 ∉ 可行集，集非空 -> 用可行集内离 ref_n 最近的一笔
可行集为空                    -> 退回 R6 的原始结果（不比 R6 更差）
全档为空                      -> None（与 R6 同）
```

`ref_n` 仍在**全档**内取，约束只做校验与修正——若改成"可行集内第 k 笔"，
k 的语义就变了，构成 train-inference mismatch。

后两条保证 R7 在任何输入上都不会比 R6 解析失败更多，**有不变式测试守护**。

### 2.3 实测收益（paired-255 真实序列，ground truth = CSV order_id）

| `ref_n` 误差 | R6 命中 | **R7 命中** | Δ |
|---|---:|---:|---:|
| 0（真值） | 100.0000% | 100.0000% | — |
| **+1** | **0.0000%** | **93.2923%** | **+93.29 pp** |
| −1 | 0.0000% | 92.4431% | +92.44 pp |
| +2 | 0.0000% | 93.2923% | +93.29 pp |
| −2 | 0.0000% | 92.2523% | +92.25 pp |

分工：**23,850 条（85.83%）约束唯一、根本不看 `ref_n`**；3,939 条（14.17%）由二者印证。

R6 之所以脆弱，是因为 `ref_n` 是**唯一**的定位信息，偏一位就要么撤错单、要么越界失败。

## 3. 一个被两个版本共同掩盖的事实

复核生成产物的 order_id 空间：

| | touch **引用到本序列 NEW** 的比例 | touch order_id 唯一值 |
|---|---:|---:|
| 26tok | **0.00%** | 220（被 4,865 条撤单复用） |
| R6.1 | **68.53%** | 4,483 |
| R7 | **68.43%** | 4,536 |

**26tok 从不撤自己生成的订单**——100% 打在 bookinit 的 220 个聚合单上。
那些单量大、反复撤也不消失，所以 live 检查永远通过。这是它 96.1435% 的第三层解释
（前两层：L1 只查时间戳不查 price/size；L2 无阈值毫秒最近邻）。

**所以"R6.1 落后 18.07 pp"比较的是一个在做真任务的系统和一个在刷不会消失的靶子的系统。**

R7 与 R6.1 的 68.43% vs 68.53% 几乎逐位相同，说明 quantity 约束**没有扭曲引用行为**，
只是让解析更准。

**R7 对 26tok 三项全胜**，保住了 R6.1 的成果。

升级为统计结论，需要同配置多次复跑，本轮未做。

## 6. 尚未解决 / 已知边界

1. **exact-target 在生成序列上没有 ground truth**。上文 §2.3 的 +93 pp 是在
   **真实**序列上用注入误差测的。生成序列里"模型本意指哪一单"无处可查，
   所以生成侧只能报 any-live-ID 与解析失败率。要测生成侧的 exact-target
   必须走 teacher-forced 通道，本轮未做。
2. **`ref_raw` 那 9.86% 仍然无解**，除非初始化簿携带窗口前订单的逐单 ID/price/size/time。
3. **`ref_age_ns` 条件编码方案未实现**。设计已定（只在约束无法唯一确定的 14.17%
   时才发，成本从 3.5 降到 0.50 token/touch），但本轮先验证零成本的部分。
4. 对抗审查提出的 22 条中，S10（没有指标测被撤订单年龄分布，存在零成本刷分路径）
   与 D7（ambiguous 导致僵尸单累积）本轮未处理。
5. 我自己那个"截断回退无效"的实验**有构造性假象**（先量化到网格再加 ±1 ns，
   `+1` 必中 `−1` 必错恰好各半，三个精度档全是精确 1/2），结论需重测。
