# R7 立项前提复核：18.07 pp 缺口的成分拆解

时间：2026-08-12T03:50Z
触发：两个独立对抗审查 subagent 的结论汇总 + 我的实地复核。
结论：**R7 当前形态的立项前提不成立，需要重新定位要修的东西。**

---

## 1. 缺口拆解（实测，非转述）

R6.1 的 reference 落后 26tok **18.0699 pp**（78.0736% vs 96.1435%），这是 R7 的立项理由。
把它拆开（数据源：`generation_quality_supervision/r6p1_s9000_paired255_20260811T1810Z/audit/generation_quality_audit.json`）：

| | R6.1 | 26tok |
|---|---:|---:|
| `cancel_rows` | 31,136 | 31,142 |
| 自报解析成功 `code_1` / `reported_reference_success` | 27,269 (87.5803%) | 29,941 |
| 重放确认 live `reference_live_id` | 24,309 (78.0736%) | 29,941 |
| **自报成功但重放非 live** | **2,960 = 9.5067 pp** | **0** |

**这个不对称只出现在 R6.1 一侧。26tok 的 reported 与 live 逐位相等，一条不差。**

按成分归类：

| 成分 | pp | R7 三个新字段能修吗 |
|---|---:|---|
| 结构天花板（目标早于 condition 窗口） | 12.1435 | **不能**，PLAN 已明确不修 |
| 自报成功但重放非 live | **9.5067** | **PLAN 只字未提** |
| 真正的 key 预测错误（残差） | **≈ 0.28** | 能修——**但只有这么多** |

> 注：0.28 pp 是 `12.4197%（自报失败率）− 12.1435%（结构天花板）` 的近似。两者分母不同
> （31,136 生成 touch vs 31,630 真实 touch），所以这是量级估计，不是精确值。
> 但即使把误差放宽一个数量级，结论不变：**R6.1 的「同价档倒数第 k 笔」这个 key
> 本身已经贴着数据天花板，可攻余量是零点几个百分点。**

R7 的原计划是：新增 `ref_size` + `ref_age_ns` + `ref_index` 三个字段、改三通道投票、
重训一个模型（约 +33% token 成本），去攻这 0.28 pp。**成本收益比不成立。**

## 2. 那 9.51 pp 是什么

> **2026-08-12T04:20Z 修正（本节原判断已被下文的日志证据推翻，保留以见推理链）**
>
> 汇总 R6.1 的 16 个 shard 生成日志，decoder 的三个分支计数是：
>
> | 分支 | 条数 | 占比 | 行为 |
> |---|---:|---:|---|
> | `ref_book` | 24,774 | 77.39% | 查簿成功 → provenance = 1 |
> | **`ref_raw`** | **3,156** | **9.86%** | **不查簿**，直接把负数码解成真实历史 order_id → provenance **也 = 1** |
> | `ref_no_book` | 4,080 | 12.75% | 解析失败，发合成号 → provenance = 3 |
>
> provenance 的写入是 `3 if ref_status == "fallback" else 1`（`varlen_bench_generate.py`），
> 所以 **`ref_raw` 被记为成功**。但生成侧的模拟簿是从 L2 快照初始化的，
> bookinit 用的是 900,000,xxx 合成 id，**真实历史 order_id 在模拟簿里根本不存在**，
> 重放必然判非 live。
>
> 对账：若 `ref_raw` 全部非 live，则 live 应等于 `ref_book` = 24,774，审计实测 24,309，
> 差 465（1.9%，来自日志口径含 EXECUTION 而审计 `cancel_rows` 不含）。**假设成立。**
>
> **所以那 9.51 pp 不是"可修的实现 bug"，而是结构天花板被 provenance 错记成了成功。**
> 它与那 12.14% 的"目标早于 condition 窗口"是同一个问题的两个投影：
> 窗口外订单在模拟簿里没有真实 id，任何 resolver 都指不到。
> 修法与结构天花板相同 —— 初始化簿时携带窗口前订单的逐单 ID/price/size/time。
>
> 对抗审查 S3 的"修了它就不用做 R7"因此**不成立**；但它的另一半判断
> —— R7 原形态攻的靶子余量很小 —— **仍然成立**。

### 原判断（已被上文推翻，保留备查）

审计 JSON 的 `r6.generation_logs.totals` 里记着：

```
book_replay_rows_different = 4047        (63,750 行中的 6.35%)
canonical_rejected         = 25
semantic_rejected          = 1
```

**生成时的簿状态与审计重放的簿状态本来就有 4,047 行对不上**，这是 R6.1 生成过程自己记录的。

这与 2,960 条"自报成功但重放非 live"是同一个病灶的两个投影：R6 的
`resolve_on_book(direction, price, k)` 按定义只会返回**当前簿上**该价档 `quantity > 0`
且 `order_id >= 0` 的第 k 笔（`scripts/varlen_bench_generate.py:115-132`），
**它在结构上不可能返回一个死单**。所以"选中的单在重放时不是 live"只能来自
生成器的簿 ≠ 重放器的簿。

26tok 一侧没有这个缺口，说明它不是评测框架的通病，而是 R6 生成路径特有的。

**这是一个工程一致性问题，不是建模问题。修它不需要新字段，也不需要重训。**

## 3. 附带发现：26tok 的撤单从不撤自己生成的新单

复核 `varlen_eval255/data_gen`（经 provenance 位域确认是 **26tok** 的产物，
它有 bit 3 = 8 的置位，即 `rel_price_ref` 与消息 price 不一致的标志；R6 的写入逻辑
只产出 1 或 3）：

| | n | order_id 范围 | 唯一值 |
|---|---:|---|---:|
| NEW (type 1) | 5,135 | 901,568,000 – 934,130,131 | 5,135 |
| touch (2/3/4) | 4,865 | **900,000,001 – 900,000,224** | **220** |

**touch 的 order_id 出现在本序列 NEW 里的比例：0 / 4,865 = 0.00%。**

两个 id 空间零交集，220 个 id 被 4,865 条撤单反复复用（平均每个被撤 22 次）。
也就是说 26tok 的撤单**从不撤它自己刚生成的订单**，全部打在 bookinit 的聚合单上——
聚合单量大、反复撤也不消失，所以 live 检查照过。

这给 26tok 的 96.1435% 提供了第三层解释（前两层是 L1 只查时间戳不查 price/size、
L2 无阈值最近邻）：**它撤的根本是一批不会消失的靶子。**

> 这一条不改变 R7 的方向，但它意味着"追赶 26tok 的 96.14%"作为目标更没有意义了。

## 4. 两个审查提出的其他阻断项

| 编号 | 问题 | 严重度 |
|---|---|---|
| S1 | **exact-target 在生成序列上没有真值**。ground truth 只存在于 `data_real`。生成时"模型本意指哪一单"无处可查。主判据不可测 = R7 没有验收标准。修法：拆成 teacher-forced（可测 exact-target）与生成（可测 any-live-ID）两条通道，两者的数永不同列 | P0 |
| S2 | `ref_index` 在 PLAN 里有**两个打架的定义**（L60 全局倒数第 k 个 NEW，1..241，熵 6.05 bit；L88 倒数第 k 个 live 同方向 NEW）。把 L60 的标签交给 L88 的解析器，实测 **40.95% 静默返回错的 order_id**（不是弃权） | P0 |
| D5 | 我自己那个"截断回退无效"的实验**有构造性假象**：脚本先把真值量化到 μs 网格再加 ±1 ns，`+1` 必中、`−1` 必错，恰好各半。三个精度档全是精确 1/2（49.0194 = 98.0388/2，47.0888 = 94.1776/2，43.7403 = 87.4807/2），是铁证。**结论需要重测** | P1 |
| D7 | ambiguous/miss → 不撤单 → 僵尸单累积，反过来污染后续解析，并改变生成簿的深度分布，可能打掉 R6.1 已全胜的 WS/KS/L1。"R7 只攻 reference 不动其他"是伪命题 | P1 |
| S7 | **R6.2 实测 51,204,974 参数（51.2M），不是 33.6M**。33.6M 是 26tok 基线的数。R6.1 的三项全胜是在 **+52% 参数**下取得的，PLAN 一个字没提 | P1 |
| S10 | 没有任何指标测**被撤订单的年龄分布**。模型只要系统性偏向引用年轻订单，exact-target 就上去、token 成本还下降，而 21 项 LOB-Bench 指标一项都不动。这是一条零成本刷分路径 | P1 |
| S11 | "26tok 的 exact-target 算不出来"这句话太强。`resolution_1 = 23,466 / 31,142 = 75.3516%` 就是一个 L1-only 的 exact-target 型基准，**零成本已有**；且 26tok 的 checkpoint 还在，teacher-forced 重跑就能导出完整的 ref 三字段 | P1 |

审查也确认了几处**站得住**的设计：纳秒 `ref_age` 在全部活单池内就是 100% 唯一（比 PLAN 声称的更强）、
`ref_size` 选 original 而非 remaining 正确、不复用 26tok 的 `price_ref` 正确
（实测 `price_reference_disagrees = 12,021 / 31,142 = 38.60%` 且从不参与 lookup）。

## 5. 修正后的优先级

原 PLAN 的步骤 3（建 worktree）之前，必须先做完这三件，否则是在错误的靶子上花算力：

| # | 动作 | 成本 | 解决 |
|---|---|---|---|
| **1** | **定位那 2,960 条 / 4,047 行的簿分歧根因** | 纯 CPU，产物已有 | 9.51 pp——**这是最大的可修成分** |
| **2** | 二选一定死 `ref_index` 定义，加 encode/decode roundtrip 一致性断言 | 改文档 + 一个测试 | 40.95% 静默错单 |
| **3** | 把主判据拆成 teacher-forced / 生成两通道，顺带跑 26tok 的 teacher-forced 对照 | 几 GPU 分钟 | 验收标准缺失 |

**如果第 1 件证明 9.51 pp 是 R6 生成路径的实现问题，那么 R7 的正确形态很可能是
「修那个问题 + 把 `quantity` 升级为硬约束」——三个新字段、三通道投票、+33% token、
重训一遍，全都不需要。**

`quantity` 硬约束已实测：零 token 成本，`side+price` 的唯一识别率从 63.8562% →
**85.8253%**，"唯一但选错" = 0。这是目前性价比最高的单项改进，且对 R6 同样适用。
