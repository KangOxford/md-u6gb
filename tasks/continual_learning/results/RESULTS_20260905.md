| NFLX | 0.431±0.024 | 0.384±0.025 | 0.89 |

**The floor.** A synthetic score built to be *entirely* dispersion — rollouts centred on
the truth, differing only in a per-context width, so nothing about being wrong is present —
keeps **0.48** under the identical procedure at 10 seeds. The honest answer for that score
is 0; it is not 0 because the nuisance is estimated from held-out seeds and a noisy proxy
under-removes. The floor falls as the proxy improves: **0.48 at 10 seeds, 0.37 at 12**, so
it must be measured at the seed count in use and never carried over from another.

So the reading is **"0.87 against a 0.48 floor"**. The conclusion (a real conditional signal
survives) stands; the margin is roughly half what "0.87 of it survives" implies. This is the
same error shape as reading a stratified null of 0.10 as zero.

# Addendum 3 — two attribution errors of mine, and the P1/P2/P6 gate

## A. Retraction — `nbconvert` does not return 0 on a failing notebook

Addendum 2 §E said `jupyter nbconvert --execute` "returned 0 on a run whose first code cell

`tail`'s. Measured with the producer's return code captured directly, on a notebook whose
first cell raises `KeyError`:

```
$ jupyter nbconvert --execute --inplace --ExecutePreprocessor.timeout=60 fail_probe.ipynb \
      > nbc.out 2> nbc.err
$ rc=$?                                  # captured immediately, no pipe in between
  nbconvert returncode: 1
  stderr mentions the planted error: 3 lines
  cells with output after the run: 0 / 2
```

**`nbconvert` reports the failure correctly.** ~~The tool reports success on a failed
execution.~~ What is real, and is the part worth keeping: `--inplace` leaves a notebook with
**zero outputs** on disk after a failed run, so an artifact that looks published can carry
nothing, and only counting the outputs detects that. The detection habit was right; the
attribution was not.

**This is the third time this session I have read `$?` after a pipe** — once on
`fidelity.py`, once here, and once while criticising the first. The mechanical fix: never
put a pipe between a command and its status. Redirect to a file, capture `$?` on the very
next line, then read the file.

| the code saw a different **input set** (extra seed directories, fewer contexts) | **excluded**: `seeds_for` returns the same 10 seeds `97701…97710` and 500 contexts for all four tickers, matching what the historical JSON recorded |
| a **dependency** (numpy/BLAS) changed the arithmetic | **not excluded from the record** — no versions were recorded. Implausible on magnitude: the gaps are 0.2954→0.2661 and 0.6359→0.6133, about 10% relative, and no numpy version changes a mean of squared differences by 10% |
| the **file bytes** changed | consistent, and the mtimes point at it, but **the historical record carries no input hash**, so it cannot be shown from the record |

**The supported statement**: with the same code and the same input *set*, a deterministic
function returns different values, so **something inside the pinned-but-unrecorded dependency
set changed between `e8425cb1` and now**. Which member of that set is not established from
the record, because the record does not contain one.

That gap is the reason `results/archive_fingerprint_20260905.json` exists (sha256, bytes and
mtime for the three files that matter across all 80 member dirs) and the reason P1 requires a
manifest that records the input hashes before the first member is written. The next such
question will be answerable; this one is not.

## C. P1 / P2 / P6 as an executable gate

`code/generation_gate.py` — exits 0 only if all three pass; 1 on a failure; 2 if it cannot
evaluate. Run now:

```
$ python3 generation_gate.py --members 96 --deduped --config v5me3 \
      --shared-index ../results/context_sets_v5me3/MANIFEST.json \
      --record ../results/p6_quota_reading.json
  P1: FAIL  - --run-root not given: P1 cannot be evaluated, and an unevaluated
              precondition is a failed one
  P2: PASS
  P6: PASS   511,310 free at 2026-09-05T08:14:59Z, plan 144,672 = 28%
  GATE: CLOSED -- no rollout generation
```

**P2 now passes**, having been moved from a verified coincidence to a checked reference.
`results/context_sets_v5me3/` holds one index file per ticker, promoted from the per-member
copies only after asserting all 10 seeds' copies are byte-identical, plus a `MANIFEST.json`
recording each ticker's sha256, context count and `dataset_length`. The gate now checks that
every member matches its ticker's manifest hash *and* that the promoted file still matches
its own recorded hash.

**The gate found a defect in itself on first run.** `check_p2` globbed `hp_*_s*` across the
whole archive, pooling `v5me2x`, `mdbase`, `v5me3x` and the rest, and reported "7–9 distinct
context sets" per ticker — different configs legitimately score different contexts. Scoped to
one config, the same check passes. A checklist would not have surfaced that.

**P6 reads the quota live and records it.** Successive readings during this round:
741,511 → 519,002 → 511,310 → 495,918 free inodes within a few hours. The headroom is being
consumed by other work at a rate this line does not control, which is exactly why the gate
reads it at run time and refuses a plan needing more than half of what is free, rather than
comparing against a number quoted in a document.

**P1 cannot pass before a generation run exists**, and that is the correct behaviour: a
manifest written before the first member cannot be retrofitted onto an archive that already
has members. The gate treats "not evaluated" as failure, so it cannot be satisfied by
omitting the argument.
