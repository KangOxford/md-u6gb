## 0. 一句话状态

GPU 侧工作已全部结束：Mamba3 scaling-law 队列 33 条训练链在磁盘上现存的**全部 436 个 checkpoint**，都已在冻结验证集 `valset_v1` 上完成交叉熵评测；据此拟合出的"最优模型规模随算力增长的指数"点估计为 0.46，但对训练链做重采样后的 95% 置信区间宽达 [0.12, 0.56]，因此该指数**尚未被数据定住**。唯一能收窄它的办法是重新训练三个小模型并保留早期 checkpoint，这一步需要人来决定是否值得，尚未执行。

## 1. 术语与量的定义

本文档反复使用下列量。为避免歧义，先逐个说明它是什么、怎么算出来的、单位是什么。

**N（参数量）**：一个模型的可训练参数总数，单位是"个"。取自评测结果 JSON 的 `num_params` 字段，例如 78M 档的实际值是 78,539,423。文中写作"78M"时是档位标签，写作 78.54M 时是真实参数量。

**D（消费 token 数）**：一个 checkpoint 在训练过程中已经处理过的 token 总数，单位是"个 token"。由该 checkpoint 的训练步数乘以每步 token 数得到，存放在结果表的 `D_tokens` 列。

**C（算力）**：训练到该 checkpoint 为止消耗的浮点运算总量，单位是 FLOP。本分析统一采用解析式 `C = 6 × N × D`，即 Kaplan 与 Chinchilla 系列工作使用的标准近似（前向两倍参数量、反向四倍参数量的乘加运算）。这里不使用实测功耗或计数器读数，全表口径一致，因此不同模型规模之间可以直接比较。

**L（验证集交叉熵）**：一个 checkpoint 在 `valset_v1` 的 30,720 样本子集上，对下一个 token 的平均负对数似然，单位是 nats/token。取自结果 JSON 的 `val_ce_mean` 字段。同一 JSON 的 `val_ce_ci95` 给出该均值的 95% 置信区间，其半宽约为 0.002 nats，这个数值在后文用作"测量噪声"的标尺。

**链（chain）**：一个 `(模型规模, 数据种子)` 组合所对应的一次完整训练 run，及其保留下来的全部 checkpoint。本队列共 12 个规模、3 个种子，因中途有个别组合缺失，实际有 33 条链。链是本分析的自然实验单位：链内的点来自同一次训练，彼此高度相关；链与链之间才是独立的。

**切片（slice）**：固定一个算力值 `C_t`，把所有算力区间覆盖 `C_t` 的链在该点的损失取出来，得到一组 `(N, L)` 点。这组点构成一条横截面曲线，理论上呈 U 形：模型太小则欠拟合，模型太大则在给定算力下训练不足，中间存在最优。

**N\*（该算力下的最优参数量）**：对切片内的 `(log N, L)` 点拟合二次函数，其顶点横坐标即为 `N*`，单位是"个参数"。**L\***：同一顶点的纵坐标，即该算力下理论上可达的最低损失，单位 nats/token。

**标度指数（slope）**：把多个切片的 `(log C_t, log N*)` 做最小二乘直线拟合，其斜率即为标度指数，无量纲。它回答"算力增长一倍时，最优模型规模应该增长多少倍"。Chinchilla 论文在通用语言建模上得到的值约为 0.5。

**左臂与右臂**：在某个切片内，参数量小于 `N*` 的点称为左臂，大于 `N*` 的点称为右臂。二次函数的顶点位置由两臂共同约束，缺了任何一侧，顶点都会变成外推而非内插。

**顶点穿底（vertex undershoot）**：拟合出的 `L*` 低于该切片实际测到的最低损失的幅度，单位 nats。定义为 `L_min_observed − L*`。这个量略大于零是正常的，因为真实最优点落在采样的 N 格点之间；但如果大到远超测量噪声，就说明顶点落进了没有数据的区域，属于拟合失效。

## 2. 数据是怎么攒出来的

分析所用的 436 个测量点分三批产生，每批解决一个不同的覆盖问题。

**第一批，132 个终末点**（本次会话之前已完成）。这批点取自每条链训练末段的 checkpoint，模型接近收敛。它们足以回答"充分训练后谁更好"，但完全无法支撑 IsoFLOP 分析，因为固定算力切片需要各种规模在**同一算力**下的表现，而终末点的算力各不相同。

**第二批，124 个早期补评**（本次会话，2026-07-31 完成）。这批点取自各链早期的 checkpoint，最小的 D 只有 2.8 亿 token。它们把每条链的算力覆盖区间向下延伸，使得低算力切片开始有点可用。以 78M 档为例，补评前每条链只有 3 个点且全部集中在末段，补评后延伸到 step 170 起的完整轨迹。

**第三批，180 个加密评测**（本次会话，2026-08-01 完成）。这批点是把磁盘上所有此前从未评过的 checkpoint 全部评完。它的作用不是扩展算力区间（逐链核对确认，这些点的最早步数都高于该链已有的最早步数，因此没有任何一条链的算力下界被拉低），而是加密链内采样，降低"链内按 log C 做线性插值"的误差。

三批合计 436 点，覆盖 33 条链、12 个模型规模（2.63M 到 293M 参数），验证集交叉熵的取值范围从 0.6003 到 2.5119 nats。逐规模的点数如下。

| Size label | 0p2M | 1M | 4M | 6M | 10M | 14M | 23M | 46M | 78M | 120M | 200M | 350M |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| Points | 11 | 12 | 26 | 49 | 55 | 54 | 42 | 45 | 63 | 45 | 18 | 16 |

至此磁盘上已无未评的 checkpoint。任何进一步的数据都必须来自新的训练，不能来自新的评测。

## 3. 结论，以及它的三层不确定度

**点估计**：标度指数为 0.4618，即算力每增长十倍，最优参数量增长约 2.9 倍。

这个数字有三个来源不同、量级差别很大的不确定度，必须分开交代。把它们混为一谈会严重误导读者，因为最小的那一项比最大的那一项窄了近七倍。

| 不确定度来源 | 幅度 | 它回答的问题 |
|---|---|---|
| Fitting method (full / window / weighted) | 0.43 to 0.49 | 在同一批数据上换一种定顶点的方法，结果差多少 |
| Trajectory sampling density (256 to 436 points) | +0.02 | 把链内采样加密一倍，结果移动多少 |
| **Chain resampling (bootstrap, 2000 draws)** | **± 0.135** | **换一批训练 run，还会得到同样的结论吗** |

链级 bootstrap 的完整结果是：均值 0.4325，标准差 0.1348，**95% 置信区间 [0.1216, 0.5573]**。

因此可以支持的表述是"最优规模随算力单调增长，指数为正且小于 1，与 Chinchilla 式的 0.5 相容"；不能支持的表述是"指数为 0.46"或"指数显著低于 0.5"。把 0.46 当作精确测量引用，会给出远超数据支撑的确定感。

## 4. 置信区间为什么这么宽

这一节解释根因，因为它同时决定了第 6 节的后续方案。

先看一个表面上的矛盾。留一法（每次去掉一条链重算）显示结果非常稳定：最大位移只有 0.036（去掉 4M-s5 链时），中位数位移只有 0.0023。但有放回的 bootstrap 却给出 ±0.135 的标准差。同一批数据，两种重采样方法给出相差近四十倍的稳定性判断。

矛盾的来源是数据的分组结构。留一法每次只丢一条链，而同一个模型规模通常有三个种子，丢掉其中一个，另外两个会顶上，顶点位置几乎不动。bootstrap 则会以不小的概率一次丢掉某个规模的全部三条链，此时如果那个规模恰好是某个切片左臂的唯一来源，该切片的顶点就失去了左侧约束。

各切片的左臂构成实测如下，可以看到问题有多严重。

| C | N* | Chains forming the left arm | Chains forming the right arm |
|---|---|---|---|
| 2.21e18 | 20.4M | 3 (all of one size, 4M) | 12 |
| 5.23e18 | 33.1M | 3 (10M, 14M, 23M, one seed each) | 11 |
| 1.24e19 | 43.7M | **1 (a single 23M chain)** | 11 |
| 2.94e19 | 70.0M | 2 (both of size 46M) | 7 |

在 C = 1.24e19 这个切片上，整条左臂只有一条链。右臂有 11 条也无济于事，因为二次函数的顶点需要两侧同时约束。

这个左右不对称不是随机的，它有一个明确的物理来源：训练时的 checkpoint 保留策略（`max_to_keep` 轮转）删除了小模型的早期存档。逐链枚举磁盘上实际保存的最早 checkpoint，可以看到分布极不对称。

| Chain | Earliest checkpoint on disk | Resulting lower bound of C |
|---|---|---|
| 78M / 120M / 350M | step 170 to 340 | 1.3e17 to 7e17 |
| 4M | step 37,670 | 2.1e18 |
| 10M | step 53,250 | 5.9e18 |
| 6M | step 65,440 | 5.2e18 |

大模型的极早期 checkpoint 恰好保留了下来，小模型的没有。于是低算力切片里能出现的，几乎全是"参数量很大但训练严重不足"的点，它们构成厚实的右臂；而本该构成左臂的小模型，在那个算力上根本没有存档。

同一个原因还造成了另一个可见症状：在 C = 2.21e18 切片上，用全部点做二次拟合时顶点穿底达 0.1064 nats，是测量噪声的 53 倍，导致该切片的 `L*` 比更高算力切片的 `L*` 还低，违反"算力更多则可达损失更低"这一硬性约束。换用只取谷底邻域点的窗口法后，穿底降到 0.0039 nats，单调性恢复，而在数据健康的三个高算力切片上，窗口法给出的顶点与全点法逐位相同。所以宽置信区间与顶点穿底是同一个数据缺口的两种表现。

## 6. 唯一尚未执行的后续实验

若 rebuttal 需要一个能定到小数点后一位的指数，唯一可行的办法是**重新训练小模型并保留早期 checkpoint**，从而加厚低算力切片的左臂。评测这条路已经走到尽头，磁盘上没有任何未评的存档了。

具体方案是在 C = 2.21e18 这个切片上补齐左臂。目前该切片左臂只有 4M 一个规模（3 条链）。若补上 6M、10M、14M 三个规模，左臂将变成 4 个规模共 12 条链，顶点的左侧约束会大幅加强，bootstrap 置信区间随之收窄。

这三个规模原本都训练过，问题仅仅是早期 checkpoint 被删了，因此重训不需要训到收敛，只需跑到对应步数即可停止：6M 约 3 万步，10M 约 2.5 万步，14M 约 2 万步。三个规模各三个种子共九个 run。**最关键的一点是必须修改 checkpoint 保留策略为全量保存**，否则重训一遍会再次把早期存档删掉，白跑。

是否值得投入这九个 run 的算力，取决于结论需要多强，这是一个需要人来拍板的取舍，不是技术问题。截至本文档写作时尚未获得授权，因此未执行。

## 8. 运维层面的坑，接手前必读

这些是本次会话实际踩到并付出时间代价的问题，重跑评测时会再次遇到。

**Slurm 多节点 srun 在这些作业上不可用。** 形如 `srun --jobid=<id> --overlap --nodes=4 --ntasks=4` 的命令会报 `Only allocated 1 nodes asked for 4`，即使 `squeue` 明确显示该作业有 4 个节点。原因与作业内已有其他 step 占用资源有关。可用的替代做法是对每个节点单独发一条 `--nodes=1 --nodelist=<node>` 的 srun，这种形式始终正常。

**GPU 利用率为 0 不等于空闲。** 判断一张卡能否使用，必须看 `nvidia-smi --query-compute-apps=pid` 返回的进程数，而不是利用率或显存。评测任务在从 squashfs 解压数据时会长时间处于 CPU 密集阶段，此时利用率显示 0% 但显存占着 80 GB 以上，随时会回到 GPU。本次会话中有一次差点误判，实际占用者是正在跑的 Transformer scaling-law 生产训练。

**worker 日志是追加写的，`tail` 出来的内容可能来自上一轮。** 脚本 `backfill_addnodes.sh` 用 `>>` 写日志以保留历史，这是有意为之，但读取时不能拿最后一行当作当前状态。判断进度的唯一可靠依据是输出目录里 `valce_*.json` 的数量，因为那是幂等的事实。本次会话中曾据此误报过一次进度。

**孤儿锁必须显式对账。** 评测队列用 `mkdir lock_<label>` 做原子抢占，跨节点靠 Lustre 仲裁。冷启动脚本 `parallel_valset.sh` 在启动时会清空所有空锁，因为它假设"此刻无人在跑"；而热态加挂脚本 `backfill_addnodes.sh` 刻意不清锁，否则会删掉其他节点上活 worker 持有的锁，导致同一个 checkpoint 被两张卡重算。代价是它无法自愈孤儿锁：如果某个 worker 抢到锁后被中断（例如宿主作业走到墙钟被 SIGTERM），锁会留下而没有对应的 JSON，后续 worker 全部跳过，队列就永远卡在未完成状态。本次会话遇到两次，处理办法是在确认全网无计算进程后，删除所有"有锁但无 JSON"的锁目录，然后重启 fan-out。

**不要用 `--export=ALL` 提交 sbatch。** 提交环境里的 `TMPDIR` 指向提交者当前所在作业的私有目录，该目录在新分配的节点上不存在，作业会在 30 秒内以 `FileNotFoundError` 失败。正确做法是在批处理脚本内部设置 `TMPDIR="${SLURM_TMPDIR:-/tmp/${USER}_${SLURM_JOB_ID}}"`。

## 9. 方法层面的教训

这些不是操作问题，而是分析设计上的判断，记录下来以免重犯。

**判据的阈值必须有物理标尺。** 顶点穿底的首版判据写成"只要 `L*` 低于最低实测值就报警"，结果六个切片里五个被标为异常，几乎没有信息量。原因是几何上顶点本就应该略低于最低实测点。改用测量噪声定标（单点 CE 的 95% 置信区间半宽约 0.002 nats，取十倍为容差）之后，唯一的真病理（穿底 0.1064 nats，即 53 倍噪声）被干净地分离出来。没有标尺的阈值不是判据，是噪声放大器。

**方法间跨度不能冒充不确定度。** 本例中三种拟合方法的跨度是 0.06，而真实的链级 bootstrap 置信区间宽 0.44，相差七倍。报告拟合结果时必须做重采样，并且重采样的单位要匹配数据的分组结构，这里是训练链而非单个数据点。

**留一法与 bootstrap 结论矛盾时，那是信号而非噪声。** 它精确地指出冗余存在于哪一层。本例中冗余在"同规模多种子"层级，不在"单条链"层级，所以只有一次性丢掉整组才会暴露脆弱性。诊断方法的选择必须匹配数据的分组结构，否则会得到虚假的稳健感。

**要区分"信息饱和"与"采样收敛"。** 补齐最后 4 个 checkpoint 后，所有数字逐位不变，说明相对于这批存档，估计已经饱和；但从 256 点到 436 点的整段加密仍使指数移动了 0.02，说明采样密度本身并未收敛。两者不矛盾：饱和的是这批 checkpoint 所含的信息量，未收敛的是采样密度，而后者需要原本就不存在的更早存档。
